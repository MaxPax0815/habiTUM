# HabiTUM Frontend — Agent Context

Read this file fully before making changes here. It is the map of the React app: routing, state, data flow to the API, and UI conventions. If you add a page, a context, or a new data-fetching pattern, update this file in the same change.

See also: [`../CLAUDE.md`](../CLAUDE.md) (whole-project overview) and [`../Backend/CLAUDE.md`](../Backend/CLAUDE.md) (the API this app talks to — route table, permission model, data shapes).

## What this is

The HabiTUM web client: habit tracking, communities, challenges/leaderboards, progress analytics (premium), and Stripe-based billing. Built with **React 19 + Vite + MUI (Material UI) + React Router v7 + Recharts + date-fns**. No Redux/Zustand/React Query — state is plain `useReducer` Context (two contexts total) plus local `useState` per page/hook. No TypeScript (despite a `tsconfig.json` being present); the whole app is `.jsx`.

## Repo shape (important, non-obvious)

- `Frontend/` is its own **separate git repository** (`Frontend/.git`), independent from `Backend/` and from the (non-git) project root. Run `git` commands from inside `Frontend/`.
- `dist/` is a committed/build output directory from a previous `vite build` — don't hand-edit it; it's regenerated by `npm run build`.

## Running it

```bash
cd Frontend
npm ci
npm run dev       # vite — http://localhost:3000, proxies /api/* to http://localhost:4000 (see vite.config.js)
npm run build     # production build → dist/
npm run lint      # eslint .
```

The dev server proxy means all frontend code calls the backend with **relative URLs** (`fetch('/api/habits')`), never an absolute `http://localhost:4000`. `VITE_API_PROXY_TARGET` env var overrides the proxy target (Docker Compose sets it to `http://backend:4000`).

Backend must be running (locally or in Docker) for anything beyond the landing/login/signup pages to work — there is no mock API layer.

## Routing map (`src/App.jsx`)

```
BrowserRouter
├── PublicLayout (renders <Header/> + <Outlet/>)
│   ├── "/"          → LandingPage
│   └── AuthLayout (centers content)
│       ├── "/login"  → Login   (redirects to /today or /manager if already authed)
│       ├── "/signup" → Signup  (redirects to /today if already authed)
│       ├── "/forgot-password" → ForgotPassword
│       └── "/reset-password/:token" → ResetPassword
└── AppLayout (renders <Sidebar user={user}/> + <Outlet/>) — only reachable if `user` is truthy, else redirected to /login
    ├── "/today"                → Home                  (habit list + create form)
    ├── "/communities"          → Communities            (browse/join/search)
    ├── "/communities/new"      → NewCommunity            (create form; gated server-side)
    ├── "/communities/:id"      → CommunityDashboard      (join/leave/delete + list of challenges)
    ├── "/challenges/:challengeId" → ChallengePage        (challenge header + Leaderboard)
    ├── "/progress"             → Progress                (premium-gated analytics dashboard)
    ├── "/profile"              → Profile                 (account status, plan cards, billing)
    └── "/manager"              → ManagerDashboard         (only if user.accountType === 'manager'; else redirect to /today)
"*" → redirect to "/today" (if logged in) or "/" (if not)
```

Auth gating is done entirely by reading `user` from `AuthContext` inline in `App.jsx`'s route elements (`user ? <X/> : <Navigate .../>`) — there is no separate `<ProtectedRoute>` wrapper component. Follow this pattern for new protected routes rather than introducing one.

## State management

Two React Contexts, both created with `createContext()` + `useReducer`, both wired in `src/main.jsx` (`AuthContextProvider` wraps `ThemeProvider` wraps `HabitsContextProvider` wraps `App`):

- **`AuthContext`** (`src/auth/AuthContext.jsx`): `{ user, dispatch }`. `user` is the full login/signup response (`firstName, lastName, username, email, accountType, subscription, stripeSubscriptionStatus, subscriptionCurrentPeriodEnd, subscriptionCancelAtPeriodEnd, subscriptionCancelAt, token`) — this is *not* just a JWT, it's a denormalized snapshot of the user's account, kept in sync via the `UPDATE_USER` action (see `useBilling.refreshCurrentUser`, which re-fetches `/api/user/me` after billing changes). Persisted to and restored from `localStorage` under the key `"user"`. Actions: `LOGIN` (replace), `LOGOUT` (null out), `UPDATE_USER` (shallow-merge). Access via `useAuthContext()` (`src/auth/useAuthContext.jsx`), never `useContext(AuthContext)` directly.
- **`HabitsContext`** (`src/context/HabitsContext.jsx`): `{ habits, dispatch }`, `habits` starts `null` (meaning "not fetched yet", distinct from `[]` meaning "fetched, none exist"). Actions: `SET_HABITS`, `CREATE_HABIT` (prepend), `DELETE_HABIT` (filter by `_id`), `UPDATE_HABIT` (replace by `_id`). Access via `useHabitsContext()` (`src/hooks/useHabitsContext.js`). Cleared on logout by `useLogout` dispatching `SET_HABITS: null`.

Communities have **no** shared context — `useCommunities()` (`src/hooks/useCommunites.js`, note the filename typo "Communites" — don't silently rename it, other files import from that exact path) is a local-state hook instantiated fresh by whichever page needs it (`Communities.jsx`, `NewCommunity.jsx`). If a future feature needs communities data in two places at once without re-fetching, that's the point where it should graduate to a Context — it hasn't needed to yet.

There is no data-fetching library (no React Query/SWR). Every page/hook manages its own `fetch` + `useState(loading/error)` + `useEffect`. New features should follow this same manual pattern for consistency, not introduce a fetching library unless asked.

One real-time exception: the community activity feed (`src/feed/useCommunityFeed.js`) uses **Server-Sent Events**. Because `EventSource` cannot send an `Authorization` header, it first POSTs to `/api/feed/ticket` (normal Bearer fetch) and opens the stream with the returned 30-second single-use ticket as a query param. Reconnects fetch a fresh ticket and pass `?lastEventId=` so the server replays missed events. If another feature ever needs live updates, reuse this ticket+SSE pattern rather than adding socket.io.

## Talking to the backend

Every authenticated request manually attaches the JWT:
```js
fetch('/api/habits', { headers: { Authorization: `Bearer ${user.token}` } })
```
There is no shared `apiClient`/`fetch` wrapper — this header is repeated in every hook/page that calls a protected route (`Home.jsx`, `HabitForm.jsx`, `HabitDetails.jsx`, `useCommunities.js`, `CommunityDashboard.jsx`, `ChallengeForm.jsx`, `ChallengePage.jsx`, `Leaderboard.jsx`, `useBillings.js`, `Progress/index.jsx`). When adding a new authenticated call, copy this exact pattern rather than adding an abstraction, unless you're asked to refactor all call sites at once.

Response shapes to know:
- `GET /api/habits` / `POST /api/habits/:id/checkin` etc. return habits **already annotated** by the backend with `checkins[]`, `progress{currentStreak,bestStreak,lastCheckinAt,lastPeriodKey,totalCheckins}`, and flattened legacy fields `streak`, `bestStreak`, `lastCheckin`, `totalCheckins` (kept for backward compatibility — see `Backend/CLAUDE.md`'s `attachProgressToHabit`). Frontend code reads both the flattened fields (`habit.streak`, `habit.lastCheckin`) and, in the newer `analytics.js`, the nested `habit.progress.lastPeriodKey` preferentially. When adding new per-habit UI, prefer `habit.progress.*` if it's period-key-exact logic, fall back to the flattened fields for simple display.
- Checkin/undo responses are `{ message, habit }`, not the bare habit — see `HabitDetails.jsx`'s `post()` helper unwrapping `json.habit`.

## The Progress/analytics.js module

This file is worth understanding on its own: it's a pure, side-effect-free, non-React computation layer that turns raw `habit.checkins[]` arrays into every metric shown on the Progress page. Notable exports and what they mean:

- `uniqueCheckinDays`, `getExpectedCount` — dedup + "how many periods should have happened since creation" (mirrors the backend's period logic but recomputes client-side from raw checkins rather than trusting `habit.progress`, except where noted below).
- `isCheckedInToday` — **prefers `habit.progress.lastPeriodKey`** (server-authoritative) and only falls back to raw-date math if that's missing; `buildPeriodKey()` in this file is a hand-mirrored copy of the backend's `getPeriodKey()` in `Backend/habit/periodUtils.js` — if the backend's period logic changes, this must change too.
- `computeHabitReadiness` — the "Habit Pulse" 0–100 score: `todayRate*0.45 + avgCompletion*0.45 + 10 − riskPenalty` (see formula comment in the file for exact weights).
- `computeOverallConsistency` / `computeOverallMomentum` / `computeOverallRecovery` — portfolio-level (all habits) signal-card metrics.
- `computeWeekdayRates`, `computeHeatmap`, `computeMonthlyStats`, `computeRecovery`, `computeBestStreak` — per-habit metrics for the selected habit's detail section, **daily habits only** (see weekly counterparts below).
- `computeWeeklyHeatmap`, `computeCheckinDayDistribution` — weekly-habit counterparts to `computeHeatmap`/`computeWeekdayRates`, used by `index.jsx` whenever the selected habit's `frequency === "weekly"`. `computeWeeklyHeatmap` returns one cell per Monday-anchored week (`{ weekStart, weekEnd, checked }`) instead of one per day, using each checkin's own `periodKey` rather than re-deriving it. `computeCheckinDayDistribution` returns the same `{ day, rate }` shape as `computeWeekdayRates` but `rate` is a *share of check-ins* (sums to ~100%), not a completion rate — a weekly habit has no "expected" weekday, so there's nothing to score pass/fail against, only a pattern of which day the user tends to check in. Both are rendered through the same components as their daily counterparts (`Heatmap`/`WeeklyHeatmap` share `heatmapCellSx`; `WeekdayBars` takes a `variant` prop to switch between threshold-colored rate bars and neutral-colored distribution bars).
- `computeDaysLeftInPeriod`, `formatPeriodDuration` — small frequency-aware helpers: the former softens the streak-at-risk banner for weekly habits (no urgency in the first days of a fresh week), the latter formats day-counts in the habit's own cadence unit (`"5d"` vs `"1.4w"`) for the Recovery display.
- `buildActionableInsight` — a priority-ordered rules engine (8 tiers, checked in order) that picks the single most relevant "Coach Insight" message. When adding a new insight rule, insert it at the correct priority tier rather than appending at the end — order matters because the function returns on first match.

If the backend ever starts returning these metrics precomputed, this file's job would shrink to formatting only — right now it duplicates real analytical work client-side on every render (memoized with `useMemo` in `index.jsx`).

## UI conventions

- **Style architecture**: `styles/tokens.js` contains raw design decisions, `styles/theme.js` applies them globally to MUI, and `styles/recipes.js` contains reusable `sx` combinations. Only `main.jsx` imports the theme itself. Components import tokens or recipes, never the old deleted `src/theme.js`.
- **MUI defaults**: Buttons and outlined inputs use a 12px radius. Cards, Papers, and Dialogs use a 16px radius and the shared divider border. Cards/Papers are outlined with no elevation by default. Chips are pill-shaped. Do not repeat these defaults in local `sx`; local overrides should express a real variant such as a selected border, status background, or compact non-surface element.
- **Color usage**: Prefer semantic MUI names (`text.secondary`, `background.paper`, `divider`, `success.main`) where they fit. Import `colors` from `styles/tokens.js` for app-specific accents such as `softBlue`, `softOrange`, and break-habit orange. Do not create another page-local palette or theme.
- **Page alignment**: Authenticated pages receive the standard 1120px `PageContainer` from `AppLayout`. Use `PageContainer` again only to intentionally narrow a page. Use `PageHeader` for normal page titles and `PageSection` for labelled content groups instead of rebuilding their spacing with ad-hoc Boxes.
- **CSS**: `index.css` is the only imported global CSS file. `habits.css` was deleted because its bare `header`, `button`, and input selectors leaked into unrelated pages. Prefer the MUI theme and `sx`; if CSS is genuinely needed, scope every selector under a feature-specific class or use a CSS module.
- **Recipes**: Use `pillButtonSx` only where a pill is intentional, `centeredPageSx` for auth layout, and `sectionTitleSx` for legacy/custom section labels that have not migrated to `PageSection`. Do not recreate the same recipe in a component.
- **Icons**: MUI icon components (`@mui/icons-material`) for structural UI (nav, buttons), but the habit-tracking UI (`HabitDetails.jsx`, `Home.jsx` stat cards, `Progress/index.jsx`) uses inline `<span className="material-symbols-outlined">icon_name</span>` (Google Material Symbols font) instead — this is a deliberate mix, not an inconsistency to "fix"; match whichever pattern the file you're editing already uses.
- **Forms**: plain controlled `useState` per field, manual `fetch` in a `handleSubmit`, no form library (no Formik/RHF). Error display is a plain `{error && <Typography color="error">{error}</Typography>}` and/or an `emptyFields` array used to redden specific `TextField`s (see `HabitForm.jsx`, `ChallengeForm.jsx`). Match this for new forms.
- **Dialogs/popups**: the global theme supplies backdrop blur, border, radius, and shadow to every MUI Dialog. Prefer `<AppDialog>` for form/custom content that also needs the shared responsive inner padding. A plain Dialog is acceptable when using standard `DialogTitle`, `DialogContent`, and `DialogActions` slots.
- **Avatars/initials**: multiple independent "first letter of name → colored circle" implementations exist (`Sidebar.jsx`'s `initials`, `Communities.jsx`'s `CommunityAvatar`, `CommunityDashboard.jsx`'s inline version, `Leaderboard.jsx`'s `getInitial`/`getAvatarColor`) — each hashes a different source string (user name vs. community name vs. rank) so they haven't been unified into one component. Don't assume changing one changes the others.

## Known quirks (don't "fix" silently — they're either intentional or pre-existing, flag before touching)

- **`index.css` repeats token colors as CSS custom properties.** React/MUI styling uses `tokens.js`; the variables remain for body/reset/focus styles. If the palette changes, update both locations or introduce a generated bridge deliberately.
- **`App.css` is unused legacy Vite CSS.** It is not imported. Remove it only as an explicit cleanup change rather than assuming it affects the current UI.
- **Full ESLint is not clean.** Existing failures include context exports triggering the Fast Refresh rule, synchronous state updates in effects, conditional hooks in Progress, and `process` in `vite.config.js`. Styling changes should still run targeted lint plus `npm run build`; do not attribute these existing failures to the theme migration.
- **`DowngradeButton.jsx` is an empty stub** (see Directory map above) — the real downgrade flow is inline in `Profile.jsx`.
- **`ChallengeForm.jsx` has no entry point in the UI yet** — there's no "New Challenge" button wired up anywhere (Communities/CommunityDashboard don't render it). If asked to add challenge creation to the UI, this component already exists and just needs a trigger + navigation wired in.
- **`useCommunites.js` and `requireCommunityCreatorAcsess.js`** (backend) are both intentionally-preserved typos in filenames that are imported by exact path elsewhere — renaming either requires updating every import site, not just the file.

## Adding a new page checklist

1. Create the component under `pages/app/` (authenticated) or `pages/public/` (unauthenticated).
2. Add a `<Route>` in `App.jsx` inside the matching layout block; follow the existing inline `user ? <X/> : <Navigate/>` pattern if it needs extra gating beyond "must be logged in" (e.g. premium-only, manager-only — see `/progress` and `/manager` for examples).
3. If it needs a nav entry, add it to `Sidebar.jsx`'s `baseNavItems`/`managerNavItems`.
4. Fetch data with a local `useState`/`useEffect`/`fetch` following the Authorization-header pattern above; only reach for Context if the data must be shared across more than one page at once.
5. Use `PageHeader` and `PageSection`, rely on MUI component defaults, and import app-specific values from `styles/tokens.js`/`styles/recipes.js`; do not add a local theme or broad global CSS.
6. Update this file's directory map and routing map.
